The boundary

A post-render step with a clear job.

Helm still renders the chart. The renderer changes only selected workload manifests and adds the Agent configuration they need.

01
⌁

Select

Discover existing Vault annotations by default. Optional selectors can add workloads by name, namespace, labels, or annotations; exclusions always win.

02
⇢

Render

Use HashiCorp's pinned annotation engine to add Agent containers, projected auth, and memory-backed volumes. Target-only selection can still generate a ConfigMap.

03
◈

Retrieve

After deployment, Vault Agent authenticates through the Pod’s ServiceAccount and writes secret files inside the Pod. Retrieved values stay out of Helm resources.

Use cases

Existing annotations. No mutating webhook.

When mutating admission is unavailable or prohibited, keep the chart and environment values intact. Helm's post-render step applies the Agent mutation before the manifests reach Kubernetes. Optional targets cover workloads without annotations.

A
▦

Restricted admission

Use existing Vault annotations without installing a mutating webhook. Review the changed Helm manifests before deployment.

B
◇

Different roles

Give an API, worker, and scheduled Job separate Vault roles and secret paths. Labels and annotations can select groups of workloads.

C
⇢

Different timing

Use init-only for a short Job, init plus sidecar for a long-running service, or sidecar-only when startup need not wait for a file.

Start here

One values file. Two ways to use it.

Existing Vault annotations need no renderer config. A plain Helm values file also works when passed to the renderer; the vault-injector section is optional. For a private Agent image or other defaults, add that section to any Helm values YAML. Both defaults and default are accepted; use one. Pass the same file to the renderer through an inline post-renderer argument or VAULT_RENDERER_CONFIG. Helm does not forward -f automatically. Helm 4 uses the plugin name vault-renderer in place of the executable path.

See complete Helm 3 and 4 commands ↗
same values.yamlHelm 3.1+
# values.yaml
replicaCount: 2
vault-injector:
  defaults:
    agent-image: registry.example/vault:2.0.4

# Option A · inline argument
helm upgrade --install myapp ./chart \
  -n production -f values.yaml \
  --post-renderer ./vault-renderer \
  --post-renderer-args=--config=values.yaml

# Option B · environment variable
VAULT_RENDERER_CONFIG=values.yaml \
helm upgrade --install myapp ./chart \
  -n production -f values.yaml \
  --post-renderer ./vault-renderer

Compatibility

The same renderer. Three Helm paths.

Helm changed its post-renderer interface across major versions. Each path keeps the renderer’s stdin/stdout contract intact.

02rendered chart

Helm 2

Helm 2 has no post-renderer. Pipe helm template into vault-renderer helm2-chart, then install the generated v1 chart as a Helm release.

Read the Helm 2 flow ↗
03direct executable

Helm 3

Pass the binary path directly to --post-renderer. Helm includes the transformed manifests in install, upgrade, and rollback history.

Read the Helm 3 flow ↗
04plugin manifest

Helm 4

Install the small postrenderer/v1 manifest, then pass its name to --post-renderer. The core binary remains independent of Helm.

Configuration reference

Supported annotations, explained.

The renderer detects agent-inject: "true" on final rendered Pod templates by default and calls the pinned vault-k8s 1.7.6 mutation engine. Helm applies environment values first; matching renderer targets can override annotations. Unknown future keys fail together. These are common examples; the full reference covers all 74 annotation names in that release.

Vault annotation suffixWhat the renderer does
roleUses this Vault Kubernetes auth role. Required for injection.
namespaceSets the Vault Enterprise namespace on Agent authentication; separate from the Kubernetes release namespace.
serviceSets the Vault address. Native annotations follow the official injector's HTTP or HTTPS behavior.
tls-secret / ca-certMounts the CA Secret into Agent containers and sets its certificate path.
agent-imageSets the image used by both Agent containers.
agent-injectAn explicit "false" disables injection for the workload.
agent-pre-populateControls the init Agent. "false" gives sidecar-only startup.
agent-pre-populate-onlyUses init-only mode, with no long-running sidecar.
agent-init-firstPlaces the Vault init Agent before existing init containers when set to "true".
agent-inject-secret-IDNames a Vault secret path. ID can be any safe destination identifier.
agent-inject-template-IDSupplies multiline Consul Template content, preserved verbatim.
agent-inject-command-IDRuns a command after the matching template renders.
agent-cache-* / agent-inject-tokenControls Agent cache and optional token sharing.
agent-inject-default-templateUses the official map-style default, or json when selected.
agent-inject-file-IDChooses the rendered filename under the shared mount.
agent-inject-perms-IDSets four-digit octal file permissions; default 0640.
agent-inject-containersLimits the secret mount to named application containers.
agent-run-as-user / groupSets non-root Agent identity and checks the Pod group.
agent-requests-* / limits-*Sets CPU, memory, or ephemeral-storage quantities on Agent containers.
template-static-secret-render-intervalControls refresh of non-leased secrets such as KV v2.

The native annotation path uses HashiCorp's pinned mutation code. Optional target-only settings retain the renderer's ConfigMap-based path.

Trust boundary

Agent instructions in the Pod.
Secrets in memory.

The renderer never contacts Vault. Native annotations produce Agent configuration inside the Pod; target-only selection generates a ConfigMap. Vault Agent retrieves secrets after the Pod starts.
